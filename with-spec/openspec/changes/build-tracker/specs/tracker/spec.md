# Spec Delta

## Purpose

Определяет поведение автономного мини-трекера учебных задач на неделю: управление задачами, валидацию ввода, расчёт итогов и фильтрацию списка с проверяемыми сценариями T1–T5.

## ADDED Requirements

### Requirement: Доменная модель и стартовое состояние
Система MUST хранить каждую задачу с полями `id`, `title`, `hours`, `done`. При старте приложение MUST содержать ровно три задачи: «Чтение» — 2 часа, `done=true`; «Практика» — 4 часа, `done=false`; «Повторение» — 2 часа, `done=false`. На основе этого состояния MUST вычисляться итоги: всего 8 часов, выполнено 2 часа, прогресс 25%.

#### Scenario: T1 — исходное состояние
- **WHEN** приложение инициализировано стартовым набором задач
- **THEN** сумма часов всех задач равна 8, сумма часов выполненных задач равна 2, прогресс равен 25%

### Requirement: Добавление, удаление и переключение статуса задачи
Система MUST позволять добавлять задачу, удалять задачу и переключать её статус `done`, при этом каждое действие MUST реально изменять данные задач и отражаться в последующих расчётах и отображении.

#### Scenario: Добавление задачи
- **WHEN** пользователь отправляет корректные данные новой задачи
- **THEN** новая задача добавляется в набор данных и участвует в расчётах итогов и фильтрации

#### Scenario: Удаление задачи
- **WHEN** пользователь удаляет существующую задачу
- **THEN** задача удаляется из набора данных и перестаёт учитываться в расчётах и отображении

#### Scenario: Переключение статуса done
- **WHEN** пользователь переключает статус `done` у существующей задачи
- **THEN** значение `done` в данных изменяется на противоположное и итоги пересчитываются

### Requirement: Валидация данных задачи
При добавлении или изменении задачи система MUST проверять: `title` после `trim` непустой; `hours` является числом от 0.5 до 24 включительно с шагом 0.5; пустое значение поля часов MUST трактоваться как ошибка и не равно нулю. При ошибке валидации система MUST показывать сообщение рядом с соответствующим полем, не применять изменение к данным и сохранять введённые пользователем значения формы.

#### Scenario: T4 — пустое название
- **WHEN** пользователь пытается сохранить задачу с пустым названием или названием из пробелов
- **THEN** отображается ошибка рядом с полем названия, данные задач не изменяются, введённые значения формы сохраняются

#### Scenario: T4 — некорректные часы
- **WHEN** пользователь пытается сохранить задачу с пустыми часами, значением вне диапазона 0.5–24 или значением не кратным 0.5
- **THEN** отображается ошибка рядом с полем часов, данные задач не изменяются, введённые значения формы сохраняются

### Requirement: Расчёт итоговых часов и прогресса
Система MUST считать итоговые часы и прогресс по всем задачам независимо от активного фильтра. Прогресс MUST вычисляться по формуле `округление(100 * сумма часов done / сумма часов всех задач)`. Если задач нет, прогресс MUST быть 0% без `NaN` и `Infinity`. Итоговые значения MUST обновляться после каждого изменения данных.

#### Scenario: T2 — отметка «Практики» выполненной
- **WHEN** в стартовом состоянии задача «Практика» отмечена как выполненная
- **THEN** выполнено 6 из 8 часов и прогресс равен 75%

#### Scenario: T5 — удаление всех задач
- **WHEN** удалены все задачи
- **THEN** сумма часов всех задач равна 0, сумма выполненных часов равна 0, прогресс равен 0% без `NaN` и `Infinity`

### Requirement: Фильтрация видимого списка
Система MUST поддерживать фильтр, влияющий только на видимый список задач. Применение фильтра MUST NOT изменять набор данных, итоговые часы и прогресс.

#### Scenario: T3 — фильтр активных не меняет прогресс
- **WHEN** в стартовом состоянии включён фильтр, показывающий только активные (не выполненные) задачи
- **THEN** в видимом списке отсутствуют выполненные задачи, но итоговые значения остаются: всего 8 часов, выполнено 2 часа, прогресс 25%

### Requirement: Интерфейс и доступность
Интерфейс MUST быть читаемым на ширине 390 px без горизонтального скролла. Все поля ввода и кнопки управления MUST иметь понятные текстовые подписи.

#### Scenario: Отображение на узком экране
- **WHEN** интерфейс отображается при ширине области просмотра 390 px
- **THEN** контент читаем, отсутствует горизонтальная прокрутка, поля и кнопки имеют видимые подписи
