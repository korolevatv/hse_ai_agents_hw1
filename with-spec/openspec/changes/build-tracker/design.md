# Design

## Context

Требуется автономный мини-трекер учебных задач на неделю (см. `proposal.md` — Why/What). Реализация ограничена нативными возможностями браузера и Node.js без CDN, внешних библиотек и API-ключей. Ожидаемые артефакты: `index.html`, `styles.css`, `app.mjs`, `domain.mjs`, `tests/acceptance.test.mjs`. Автоматические проверки T1–T5 задают контракт поведения, которому должны соответствовать реализации.

## Goals / Non-Goals

**Goals:**
- Чётко разделить доменную логику (данные, валидация, расчёты, фильтрация) и интерфейс (рендер, события, DOM).
- Обеспечить детерминированное стартовое состояние и расчёты, покрываемые тестами T1–T5.
- Реализовать понятную валидацию формы с сохранением введённых значений при ошибке.
- Обеспечить читаемый интерфейс на ширине 390 px без горизонтального скролла.

**Non-Goals:**
- Персистентное хранение (localStorage/сервер), синхронизация, авторизация.
- Использование фреймворков, сборщиков, CDN и внешних зависимостей.
- Расширенные функции (редактирование задач, сортировка, теги, дедлайны) сверх требований brief.

## Decisions

### 1. Разделение `domain.mjs` и `app.mjs`
- **Решение:** `domain.mjs` содержит чистые функции и/или фабрики состояния без доступа к DOM; `app.mjs` отвечает за инициализацию, обработку событий, отображение ошибок и рендер.
- **Почему:** упрощает unit/acceptance-проверки логики в Node.js, снижает связанность и делает поведение воспроизводимым для T1–T5.
- **Альтернативы:** вся логика в `app.mjs`. Отклонено: сложнее тестировать доменные правила без браузерного окружения.

### 2. Модель данных и идентификаторы
- **Решение:** задача — объект `{ id, title, hours, done }`. `id` — уникальный строковый/числовой идентификатор, генерируемый при создании (например, монотонный счётчик или `crypto.randomUUID()` при наличии, с детерминированным fallback). Стартовый набор создаётся функцией-фабрикой в домене с фиксированными значениями.
- **Почему:** явная идентификация нужна для удаления/переключения конкретной задачи; фабрика стартового состояния гарантирует T1.
- **Альтернативы:** идентификация по индексу массива. Отклонено: хрупко при фильтрации и удалении.

### 3. Валидация ввода
- **Решение:** отдельная функция валидации (например, `validateTaskInput({ title, hours })`) возвращает нормализованные данные или список ошибок по полям.
  - `title`: `trim()`; пустая строка → ошибка.
  - `hours`: пустая строка/`null`/`undefined` → ошибка; парсинг числа; проверка конечности, диапазона `[0.5, 24]` и шага 0.5 (например, `Number.isInteger(hours * 2)` с учётом числовой точности).
- **Почему:** единая точка правил покрывает T4 и исключает трактовку пустого значения как 0.
- **Альтернативы:** валидация разрозненно в обработчиках UI. Отклонено: дублирование и риск расхождений.

### 4. Расчёт итогов
- **Решение:** чистая функция расчёта (например, `calculateTotals(tasks)` → `{ totalHours, doneHours, progress }`).
  - `totalHours = sum(hours)`, `doneHours = sum(hours where done)`.
  - `progress = totalHours === 0 ? 0 : Math.round(100 * doneHours / totalHours)`.
- **Почему:** соответствует формуле из brief, гарантирует 0% без `NaN/Infinity` при пустом списке (T5) и стабильные результаты (T1, T2).
- **Альтернативы:** расчёт на лету в рендере без выделенной функции. Отклонено: хуже тестируемость.

### 5. Фильтрация
- **Решение:** состояние фильтра (`all | active | done`) хранится отдельно; функция `getVisibleTasks(tasks, filter)` возвращает подмножество для отображения. Итоги всегда считаются от полного массива `tasks`.
- **Почему:** прямо удовлетворяет требованию «фильтр влияет только на видимый список» и T3.
- **Альтернативы:** хранить отфильтрованный массив как источник истины. Отклонено: ломает расчёт прогресса.

### 6. Интерфейс и обработка ошибок формы
- **Решение:** `index.html` содержит семантическую разметку формы (label + input), список задач, блок итогов и контролы фильтра. `app.mjs` при ошибке валидации рендерит текст ошибки рядом с соответствующим полем (например, `<span>`/`<p>` с привязкой к полю) и не сбрасывает значения инпутов. `styles.css` использует гибкую вёрстку (flex/grid, `%/max-width`) и медиазапросы при необходимости, чтобы на 390 px не было горизонтального скролла.
- **Почему:** удовлетворяет требованиям UX/доступности (подписи, видимые ошибки, сохранение ввода) и адаптивности.
- **Альтернативы:** `alert()` для ошибок. Отклонено: не «рядом с полем» и хуже UX.

### 7. Тестирование (T1–T5)
- **Решение:** `tests/acceptance.test.mjs` использует `node:test` и `node:assert/strict`, импортирует доменные функции из `domain.mjs`. Тесты покрывают: T1 стартовые итоги, T2 переключение «Практики», T3 неизменность итогов при фильтре active, T4 ошибки валидации для пустого названия и некорректных часов, T5 итоги после удаления всех задач.
- **Почему:** нативный раннер Node.js без зависимостей; проверка контракта на уровне домена обеспечивает воспроизводимость.
- **Альтернативы:** браузерные e2e. Возможны дополнительно, но не обязательны по brief; базовый контракт закрывается доменными тестами.

## Risks / Trade-offs

- [Расхождение DOM и домена] → Держать домен источником истины, рендерить UI как проекцию состояния; покрыть ключевые сценарии тестами.
- [Числовая точность при шаге 0.5] → Проверять шаг через целочисленное представление (`hours * 2`) и избегать сравнений float напрямую.
- [Разное понимание «округление»] → Использовать `Math.round` как стандартное округление до ближайшего целого; зафиксировать в тестах ожидаемые значения (25%, 75%).
- [Ограниченная проверка визуальной адаптивности автотестами] → Закрепить требование в design/tasks и проверить вручную на 390 px.

## Migration Plan

Не применимо: новая автономная реализация без существующих данных и развёртывания. Откат — удаление добавленных файлов изменения.

## Open Questions

Нет. Все существенные для реализации и проверок T1–T5 решения определены brief и данным дизайном.
